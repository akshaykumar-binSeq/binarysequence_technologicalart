# 2. Editorial Rules and Governance

## Rule 1 — Say What Is True Now
Use present tense exclusively for operational capabilities, deployed systems, and confirmed tools. Explicitly badge all other initiatives as `In Development`, `Experimental`, or `Planned`.

## Rule 2 — Complexity Belongs in the Architecture
Never overwhelm the visitor with unnecessary technical jargon on first exposure. Present the human and business benefit first. Progressively disclose architecture, domain boundaries, and technical trade-offs only when requested.

## Rule 3 — Eliminate Speculative Guarantees
Banned terms: *"100% secure,"* *"zero bugs,"* *"unlimited support,"* *"future-proof,"* *"guaranteed scalability."* Replace them with verifiable practices: *"reproducible builds,"* *"isolated failure domains,"* *"written maintenance plans,"* and *"documented recovery procedures."*

## Rule 4 — The 5–15 Year Horizon is Planning, Not an Unlimited Warranty
Architectural systems are designed for a 5–15 year operational horizon (clean boundaries, decoupled dependencies, structured data ownership). This does not constitute an unconditional guarantee of free maintenance. Ongoing maintenance is governed by written service agreements.

## Rule 5 — Continuity and Handover Protocol
Address the single-practitioner reality transparently. Emphasize that all engagements deliver complete source code ownership, structured repositories, infrastructure-as-code definitions, encrypted backup scripts, and step-by-step handover documentation so the client is never trapped by vendor lock-in.

## Rule 6 — Evidence Before Metrics
Never publish arbitrary percentages, unmeasured uptimes, or unsubstantiated case studies. Any published metric must document its measurement method, test environment, sample size, and limitations.

## Rule 7 — Two-Scroll Scannability
Primary landing views must communicate their core value within 2–3 viewport scrolls on standard desktop displays. Detailed breakdowns must use accessible inline expanders or route cleanly to Tier 2 deep dives.

### Purpose
Demystify the engineering process through an accessible, inspectable 11-step lifecycle. Reassure commercial clients that their investment follows structured, reproducible engineering gates.

### Section A — Introductory Narrative
- **Eyebrow:** `THE SEQUENCE METHOD`
- **Headline:** `From first principles to continuous evolution.`
- **Narrative:** High-quality software is never created by jumping straight into code. We use an 11-step sequence that begins by analyzing the human context and ends with long-term operational stewardship.

### Section B — The 11-Stage Sequence (Inspectable Modules)

```
01. OBSERVE      ──► 02. QUESTION     ──► 03. UNDERSTAND   ──► 04. MODEL
       ▲                                                           │
       │                                                           ▼
08. MEASURE      ◄── 07. ENGINEER     ◄── 06. CREATE       ◄── 05. ARCHITECT
       │
       ▼
09. REFINE       ──► 10. OPERATE      ──► 11. EVOLVE
```

1. **OBSERVE (Empirical Discovery):** Analyze the actual human workflow, existing operational bottlenecks, and real-world user behaviors before writing a line of code or selecting software frameworks.
2. **QUESTION (Hypothesis & Scrutiny):** Challenge default technical assumptions. Do you actually need a microservices architecture? Is a dedicated mobile app required, or is an accessible progressive web application superior?
3. **UNDERSTAND (Business Definition):** Define precise business rules, operational constraints, compliance mandates, data protection requirements, and quantifiable success metrics.
4. **MODEL (Domain Modeling):** Map the problem space into ubiquitous domain language, core entities, aggregates, and bounded contexts following Domain-Driven Design principles.
5. **ARCHITECT (System Specification):** Select the system topology, database schemas, API contracts, third-party adapters, and deployment infrastructure. Document critical decisions via Engineering Decision Records (EDRs).
6. **CREATE (Ergonomic UX Design):** Shape the user experience through interactive wireflows, typography hierarchies, and tactile layout compositions. Focus on cognitive ease and zero visual friction.
7. **ENGINEER (Discipline Implementation):** Write clean, idiomatic code with clear boundaries, comprehensive unit and integration tests, strict static analysis, and automated CI/CD builds.
8. **MEASURE (Empirical Verification):** Verify system performance against strict technical benchmarks: API latency, Core Web Vitals, error rates, and security vulnerability scans.
9. **REFINE (Evidence-Driven Polish):** Eliminate edge-case bugs, optimize database queries, refine micro-interactions, and ensure responsive layouts perform flawlessly across all screen sizes.
10. **OPERATE (Production Stewardship):** Deploy to hardened production environments with structured logging, uptime monitoring, automated database backups, and client-accessible runbooks.
11. **EVOLVE (Adaptive Lifecycle):** Continuously review system performance against changing business needs, safely updating dependencies, upgrading infrastructure, and adding capabilities as evidence dictates.

### Section C — Inspectable by Design
- **Headline:** `Every engineering decision leaves an audit trail.`
- **Narrative:** We believe clients should understand why their system is built the way it is. Every major architectural decision is documented with its business context, evaluated alternatives, cost implications, and operational trade-offs.

   All bespoke source code, domain models, database migration scripts, UI component libraries, and documentation produced under commercial agreements are transferred fully to the client. Repositories are hosted under client-owned organizations from project inception.
2. **Infrastructure as Code (IaC) & Account Isolation:**
   Production cloud infrastructure (servers, databases, DNS, email routing) is provisioned inside client-owned cloud accounts (AWS, Google Cloud, Supabase, Cloudflare). Binary Sequence maintains administrative access only as an authorized technical operator; the client retains master credential authority.
3. **Automated Recovery & Encrypted Backups:**
   Every production database includes automated, off-site encrypted backup configurations. Step-by-step restoration runbooks are verified and documented so any competent systems engineer can restore operations in the event of an outage.
4. **Comprehensive Handover Runbooks & Escrow Compatibility:**
   Every delivered system includes an *Operational Runbook* detailing local development setup, environment secrets management, deployment triggers, and external service inventories. For mission-critical deployments, formal code escrow agreements can be established with agreed release conditions.

### Section C — Maintenance Agreements vs. SLAs
- **Vital Stewardship (Maintenance):** Scheduled dependency patching, vulnerability scanning, security audits, and infrastructure health reviews.
- **Service Level Agreements (SLAs):** Where required by institutional clients, contractual uptime targets, response windows, and emergency escalation paths are formalized in writing before launch.
